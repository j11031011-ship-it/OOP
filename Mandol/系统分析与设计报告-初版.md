# Mandol 融合索引增强：系统分析与设计报告

- 课程：《大模型辅助的面向对象软件分析、设计与开发》大作业
- 方向：融合索引增强（语义相似 + 属性约束 + 时间约束 + 关系约束）
- 阶段：阶段 1；代码基线为当前 HEAD（P0–P4 已落地）
- 关联文档：《优化方向.md》《实现总结.md》

## 0. 摘要

**问题**：Mandol 现有融合检索是“多路并行召回 + 分数融合（并集）”。语义相似之外的条件——
属性、时间、关系——无法作为约束进入检索流程；组合查询只能靠结果后置过滤或全库线性扫描，
既不能保证召回池中存在满足条件的单元，也没有统一的表达与调度机制。

**方案**：约束下推式组合检索（Constrained Hybrid Retrieval）。用声明式 `QueryConstraints`
描述组合条件；由 `BaseConstraintResolver` 策略族把每类约束独立求解为统一的 `CandidateSet`
（支持交/并/差）；`ConstraintAwarePlanner` 依据选择率决定“候选集下推（pre-filter）”还是
“检索后过滤（post-filter）”。倒排索引、时间有序索引和图 BFS 都只负责生成候选集，可以替换
实现。初版语义为四类叶子谓词的扁平 AND，OR/NOT 组合树保留为扩展点。

**关键核验**：BM25/SPLADE/Cosine 三路检索器均已原生支持 `candidate_uids`，三路后端无需修改
即可接入约束；`filter_memory_units` 是线性后置过滤，没有接入多态体系；`SemanticGraph` 存在三处
调用未定义方法的断链 API；时间戳实际位于 `raw_data["timestamp"]`，而非 `metadata`；
`created_time` 在写入路径不填充。这些事实直接决定了方案形态：扩展点落在既有
`candidate_uids` 签名上，图只作为**约束源**而非第 4 路召回，关系 BFS 由本项目实现，不依赖
断链 API。

**当前实现**：P0–P4 主线已落地，全量测试 **103 项通过**。合成语料（2000 units）上，高选择性
用例 recall@10 由 **16.7% 提升到 100%**，宽约束画像由 **51.0% 提升到 100%**；属性/时间/关系
一跳的约束解析层相对线性扫描加速约 **40–87 倍**；索引增量维护约 **7.8 μs/单元**。真实数据集
实验尚未执行，上述数字不能外推为真实语义效果。

## 1. 系统理解

### 1.1 代码结构

Mandol 是面向大模型智能体的分层记忆系统：以内存为中心，融合键值存储、稠密/稀疏向量索引
与图结构（README_CN.md:52-54）。核心模块如下。


| 模块                                             | 职责                                                 | 关键类/函数                                                                                                             |
| -------------------------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| `core/`                                          | 记忆模型与融合存储主类                               | `MemoryUnit`、`SemanticMap`、`SemanticGraph`、`MemorySpace`                                                             |
| `retrieval/`                                     | 进程内多路检索管线                                   | `BaseRetriever` 族（BM25 / SPLADE / Cosine / Graph）、`MultiRetriever`、`ScoreFusion`、`RerankerManager`、`QueryBundle` |
| `triple_retrieval/`                              | 三塔编排：路由分发、统一重排、量化打包               | `TripleTowerRetriever`                                                                                                  |
| `hierarchical/`、`episodic/`、`entity_relation/` | 三塔各自的检索器实现                                 | `HierarchicalRetriever`、`EpisodicMemoryRetriever`、`EntityRelationGraphRetriever`                                      |
| `memory_router/`、`quantification/`              | 查询意图路由、充分性判断、级联剪枝、Token 约束上下文 | `LocomoTowerRouter`、`SemanticQuantifier`、`CascadePruner`                                                              |
| `auto_builder/`、`cluster/`、`llm/`              | 高阶记忆构建、聚类策略、LLM 客户端                   | `Orchestrator`、`BaseClusterer`、`BaseProvider`                                                                         |
| `storage/`                                       | RocksDB 分层持久化                                   | `TieredStorageManager`、`RocksDBPayloadStore`                                                                           |
| `constraints/`（新增）                           | 约束值对象、Resolver 策略族、候选集代数、调度与降级  | `QueryConstraints`、`CandidateSet`、`ConstraintAwarePlanner`、`FallbackPolicy`                                          |
| `indexes/`（新增）                               | 属性/时间索引策略族与持久化注册表                    | `MetadataIndex`、`HashIndex`、`SortedIndex`、`TimestampNormalizer`                                                      |

评测侧资产（`benchmark_locomo/`、`benchmark_longmemeval/` 的 task_eval 脚本）**直连**
`MultiRetriever.smart_search`（locomo_benchmark_episodic.py:157），可直接作为后续真实数据实验的入口。

### 1.2 核心对象

**（1）`MemoryUnit`（memory_unit.py:10-65）——记忆原子容器**

- `__slots__` 固定 7 个属性：`uid`、`raw_data`、`metadata`、`embedding`、`sparse_embedding`、
  `text_cached`、`created_time`；
- `raw_data` 的 property setter 在写入时重建 `text_cached` 派生视图，封装不变量；
- 检索文本按 `text_content / content / description / summary / title / message` 优先级提取，
  否则拼接字符串字段；
- `created_time` 默认 `None`，写入路径不填充，仅序列化加载时恢复（semantic_map.py:3054），
  因此不能作为时间约束的默认字段。

**（2）`SemanticMap`（semantic_map.py）——融合存储主类**

- 进程内 dict 存 unit（`memory_units`）、`uid ↔ int_id` 双向映射、FAISS 稠密索引、空间成员关系、
  稀疏检索器增量句柄（`_multi_retriever`）；
- 同时承担存储、索引、过滤、序列化四类职责，是典型的“上帝类”；
- 现有但未接入多态体系的能力：`filter_memory_units`（semantic_map.py:3169）支持 10 种操作符的
  线性过滤，但它是后置扫描、不查 `metadata`、无分页，也没有挂进多态调度。

**（3）`SemanticGraph`（semantic_graph.py）——结构关系层**

- rustworkx 有向图：节点为 memory_unit / memory_space，边带 `type` 与属性；
- 关系属性仅保留 LRU 热缓存；`add_relationship`（semantic_graph.py:610）是关系维护的唯一入口；
- 对 `SemanticMap` 采用门面包装；新增的 `search_constrained`（semantic_graph.py:1115）是组合检索
  的公共入口。

**（4）检索接口体系（retrieval/retrieval_interface.py）——多态扩展点**

```
BaseRetriever(ABC)        search(query, top_k, **kwargs) + get_method_type()
 ├─ BM25Retriever / SPLADERetriever
 ├─ CosineRetrieverAdapter（把 SemanticMap 旧 API 包装为 BaseRetriever）
 └─ GraphRetriever
RetrievalInterface(ABC)       存储层契约（SemanticMap 实现）
MultiRetrievalInterface(ABC)  多路协同契约（MultiRetriever 实现）
```

关键衔接点：BM25 / SPLADE / Cosine 的具体实现均显式声明
`search(query, top_k, candidate_uids=None, space_names=None)`，抽象基类以 `**kwargs` 透传——
**候选集下推无需修改任何后端**（bm25_retriever.py:1499-1574、splade_retriever.py:959-997、
semantic_map.py:2167）。这是方案最重要的复用点。

### 1.3 核心执行流程

**（1）写入流程（add / batch 增量维护链）**

```
add_unit(unit, space_names, index_update_mode="incremental")   semantic_map.py:1304
 ├─ 查重 → 生成 dense embedding → 写入 memory_units 与空间成员
 ├─ 缺稀疏向量 → 生成 SPLADE
 ├─ _apply_index_update_mode(...)                               semantic_map.py:1264
 │    incremental: FAISS remove_ids + add_with_ids；BM25/SPLADE add_units
 └─ 记账 → _trigger_tiered_eviction_if_needed
```

`batch_add_units` 与单条路径同构：批量 encode → 批量写 payload / 空间成员 / SPLADE →
`_apply_index_update_mode(all_added_units)` → 换页检查。`delete_unit` 依次删除 payload、外部存储、
空间成员、FAISS 向量、BM25/SPLADE 反向条目，并记账 `_deleted_units`。

**结论**：写入路径尾部已有三个现成挂载点——FAISS、BM25/SPLADE 增量、换页触发。新增索引只需
与 `_incremental_aux_retriever_add` 并列挂载，并沿用空间缓存的版本失效方式即可。

**（2）检索流程（smart_search 主链路）**

```
smart_search(query, top_k, **kwargs)                 advance_retriever.py
 ├─ 入口规范化，显式剔除 GRAPH_TRAVERSAL             :937
 ├─ QueryBundle 缓存 dense/splade/bm25 编码
 ├─ _execute_base_retrieval                          :1154-1195
 │    space_names 为显式参数；candidate_uids 等条件走 kwargs；
 │    每路扩容 max(top_k * 3, 50)
 ├─ BM25 / SPLADE / Cosine 并行召回
 ├─ ScoreFusion（RRF / 加权 / MMR）
 └─ 可选 Reranker → 可选 GraphContextExpander
```

**结论**：`candidate_uids` 从 `smart_search` 到三路后端已经贯通；图证据只能通过“约束源 +
后置图扩展”进入，不能作为召回源加入 `smart_search`。

**（3）换页流程（RocksDB 分层持久化）**

```
高水位触发 → _select_cold_l1_uids                     semantic_map.py:619-629
           → _remove_from_l1_for_tiered_swap          semantic_map.py:631-653
               仅 del memory_units[uid]；显式保留 FAISS、uid↔int_id、空间、图；
               _storage_uids.add(uid) 标记“payload 在持久层”
           → 命中冷 uid 时 get_unit 按需 page-in       semantic_map.py:655-670
```

**结论**：换出是“payload 级”而非“索引级”的——索引常驻进程内、倒排按 uid 存值，与属性/时间
索引正交；这支持了“索引不因换页失效”的设计假设。

### 1.4 现有能力与缺口


| 访问形态     | 现成能力                                                        | 缺口                                                |
| -------------- | ----------------------------------------------------------------- | ----------------------------------------------------- |
| 语义相似     | 三路召回 + RRF/加权/MMR 融合 + 重排                             | —                                                  |
| 精确标识     | uid 精确存取、空间成员过滤（`candidate_uids` 支持空间子集检索） | —                                                  |
| 属性约束     | `filter_memory_units` 后置线性扫描（10 操作符）                 | 游离于多态体系之外；不查 `metadata`；无索引、无分页 |
| 时间约束     | 时间戳随 payload 存储                                           | 字符串、格式异构、无规范化、无有序索引              |
| 关系查询     | `GraphRetriever` 独立节点/边检索；图上 BFS 能力                 | 与语义检索平行，不能作为附加约束；部分图 API 断链   |
| **组合查询** | **无**                                                          | **没有“交集 + 谓词下推”的表达与调度机制**         |

## 2. 需求分析

### 2.1 需求来源与目标

课程要求支持“与给定内容语义相近、发生于某时间之后，并且属于某实体邻居的记忆”这类组合查询，
并比较检索效果、访问开销与维护成本。可以归纳为四条可验证需求：

1. **R1 表达能力**：一条语句表达“语义 + 属性 + 时间 + 关系”的组合约束，而非分步手工过滤；
2. **R2 正确性**：返回结果必须**硬满足**全部约束，而不是“尽量”；
3. **R3 效率**：高选择性约束下避免全库扫描与无效向量比对（pre-filter 下推）；
4. **R4 衔接与成本**：不破坏现有检索流程与行为；构建、增量、内存成本可量化。

### 2.2 目标用例


| 用例           | 查询语义                                                                  | 现状                                 | 目标                           |
| ---------------- | --------------------------------------------------------------------------- | -------------------------------------- | -------------------------------- |
| U1 语义 + 时间 | “与内容 C 语义相近、且发生在 T 之后的记忆”                              | 先语义检索再自行过滤，或全库线性扫描 | 一条 `search_constrained` 完成 |
| U2 语义 + 关系 | “与 C 语义相近、且属于实体 E 邻居的记忆”                                | 图检索与语义检索平行，无法组合       | 同上                           |
| U3 全组合      | “与 C 语义相近 + 发生在 T 之后 + 属于实体 E 的 1-hop 邻居 + 属于空间 S” | 不支持                               | 一条语句完成，且延迟可接受     |

### 2.3 三个缺口与核心结论

1. **属性约束缺口**：`filter_memory_units` 是现成的 10 操作符过滤器，但为游离的线性后置过滤
   （取值顺序 `getattr(unit, field)` → `unit.raw_data.get(field)`，不查 `metadata`；无 limit/分页），
   没有挂进 `BaseRetriever` 多态调度。
2. **关系约束缺口**：`search_graph_relations` 无 seed 时全图 O(E) 枚举，无“关系类型 → 边”倒排；
   “属于某实体邻居”无法下推到向量/词法检索；带 seed 路径还依赖未定义方法。
3. **时间约束缺口**：时间戳主要为 `raw_data["timestamp"]` 字符串，格式随数据集而异，
   无规范化与有序索引。

**核心结论**：底层 pre-filter 管道已齐备，现有融合范式是**“并集 + 分数融合”**；组合查询需要的
是**“交集 + 谓词下推”**范式。缺失的是**候选集生成层**（属性/时间/关系谓词）与**调度层**
（多约束协调、执行路径选择）。

### 2.4 非功能需求


| 类别     | 要求                                               | 验证方式                        |
| ---------- | ---------------------------------------------------- | --------------------------------- |
| 正确性   | 约束硬满足；与“全量检索 + 线性过滤”基线等价      | 集成测试断言 + 等价性对拍       |
| 性能     | 高选择性场景避免全库扫描；pre/post-filter 自动切换 | 候选占比扫描曲线实验（P50/P99） |
| 兼容性   | 不传约束时行为与现状一致；底层检索器零修改         | 现有 `pytest tests/` 回归       |
| 维护成本 | 索引按需启用（注册制）；增量维护挂载于既有写入链   | 构建/增量/内存三项指标          |
| 可测试性 | 全部单测离线可跑（Dummy 模型 + monkeypatch）       | 新增测试套件                    |

## 3. 对象建模

### 3.1 建模原则

- **值对象隔离**：查询条件与候选集都是不可变值对象（`QueryConstraints`、`CandidateSet`），
  避免裸 dict 传参依赖字符串约定、缺少类型保障。
- **策略多态**：每类约束、每种索引实现都是策略族中的一个子类，对上层统一接口编程；
  新增约束或索引类型不需要修改调度代码（OCP）。
- **组合优于继承**：不改 `SemanticMap`（职责已过重，违反 SRP）、不派生索引子类；
  索引与调度均以组合方式注入，生命周期与存储主类解耦。

### 3.2 新增对象及职责


| 新增类                                    | 形态                              | 设计模式         | 职责与关键点                                                                           |
| ------------------------------------------- | ----------------------------------- | ------------------ | ---------------------------------------------------------------------------------------- |
| `QueryConstraints`                        | `@dataclass(frozen=True)`         | 值对象           | `metadata_filters` / `time_range` / `relation` / `space_names`；四类叶子谓词的扁平 AND |
| `TimeRange`                               | 值对象                            | 值对象           | `start` / `end` / `field="timestamp"`；闭区间；参数声明期校验                          |
| `RelationConstraint`                      | 值对象                            | 值对象           | `seed_uids` / `max_depth=1` / `relation_types` / `direction`；声明期校验               |
| `CandidateSet`                            | 值对象                            | 值对象           | `frozenset` uid 集合 + `source` + `total`；`selectivity`；`intersect/union/difference` |
| `BaseConstraintResolver`                  | 抽象基类                          | 策略模式         | 统一接口 `resolve() -> CandidateSet`，并暴露 `source` 供审计                           |
| `MetadataConstraintResolver`              | 子类                              | 策略 + 适配器    | 属性条件 → `MetadataIndex`；索引不可用时退回统一取值语义的扫描                        |
| `TimeRangeConstraintResolver`             | 子类                              | 策略             | 时间窗口 → `SortedIndex` bisect；无索引时按归一化 epoch 扫描                          |
| `RelationConstraintResolver`              | 子类                              | 策略             | 关系约束 → 图上限制方向/深度/类型的 BFS                                               |
| `SpaceConstraintResolver`                 | 子类                              | 适配器           | 包装现有空间成员逻辑，使空间条件与其他谓词同构                                         |
| `ConstraintGroup`（预留）                 | 组合                              | 组合模式         | AND/OR/NOT 树；**仅设计预留，本阶段未实现**                                            |
| `MetadataIndex`                           | 独立类，被 `SemanticMap` 组合持有 | 门面 + 简单工厂  | 字段注册与路由、增删、lookup、选择率；`field_kinds` 可持久化                           |
| `BaseIndex` / `HashIndex` / `SortedIndex` | 策略族                            | 策略（索引多态） | 倒排等值/包含；epoch 有序窗口与精确选择率                                              |
| `TimestampNormalizer`                     | 独立策略类                        | 适配器           | 多格式时间字符串 → epoch float；容错解析、缺省丢弃、边界快速失败                      |
| `ConstraintAwarePlanner`                  | 独立类，被图门面组合持有          | 策略调度器       | 求交、选择率判定、pre/post 选择、池扩容、降级与审计                                    |
| `FallbackPolicy`                          | 值对象                            | 策略参数         | 退化候选集处理：`return_empty`（默认）或 `drop_constraint`（记录丢弃项）               |

### 3.3 静态结构：双轨多态

```
SemanticGraph ─门面─> SemanticMap ─组合─> MultiRetriever ──> BM25 / SPLADE / Cosine
      │                                                        ▲
      │ search_constrained(query_text, constraints)            │ candidate_uids（既有签名）
      ▼                                                        │
ConstraintAwarePlanner ───────── 候选集透传 ──────────────────┘
      │
      ├── QueryConstraints（四类叶子谓词的扁平 AND；OR/NOT 为扩展点）
      │       └── BaseConstraintResolver(ABC) 策略族
      │               ├─ MetadataConstraintResolver ──> MetadataIndex ──> HashIndex / SortedIndex
      │               ├─ TimeRangeConstraintResolver ─> SortedIndex + TimestampNormalizer
      │               ├─ RelationConstraintResolver ──> SemanticGraph.rx_graph（限制深度 BFS）
      │               └─ SpaceConstraintResolver ─────> MemorySpace 成员关系
      └── CandidateSet（uid 集合 + 选择性估计）——两条多态轨道的解耦媒介
```

“双轨多态”指：约束解析多态（`BaseConstraintResolver` 族）× 索引实现多态（`BaseIndex` 族）。
两轨通过 `CandidateSet` 值对象解耦，均可独立扩展。

### 3.4 动态交互：U3 一次查询的执行时序

1. 应用调用
   `search_constrained(query_text=C, constraints=QueryConstraints(time_range=..., relation=RelationConstraint(seed_uids=[E], max_depth=1), space_names=[S]))`；
2. `SemanticGraph` 门面接收并委托 `ConstraintAwarePlanner`；
3. Planner 将约束拆解为叶子谓词，各 Resolver 独立求值：
   - 元数据 → `MetadataIndex.lookup` → `CandidateSet`（含选择性估计）；
   - 时间 → `SortedIndex` 区间 → `CandidateSet`（精确选择率）；
   - 关系 → 从 E 出发限制深度/方向/类型的 BFS → `CandidateSet`；
   - 空间 → 空间成员集合 → `CandidateSet`；
4. 各叶子谓词按 AND 语义求交，得到最终候选集；
5. Planner 依据 `|候选集| / 总量` 与阈值（默认 20%）选择 pre-filter 或 post-filter；
6. `smart_search` 完成语义召回、融合与重排；结果再次按候选集校验后截断 `top_k`。

> 调用方显式传入的 `candidate_uids` 同样被视为约束：即使没有声明 `QueryConstraints`，
> 最终结果也要按它复核，因为图扩展等环节可能带回候选集之外的单元。

### 3.5 设计取舍


| 取舍点           | 选择                                 | 理由                                                                                  |
| ------------------ | -------------------------------------- | --------------------------------------------------------------------------------------- |
| 约束逻辑放哪     | 独立 Resolver 族 + Planner           | 不放 `BaseRetriever` 子类，否则每路重复实现（违反 DRY）；约束求值与评分召回是两类职责 |
| 索引挂哪         | `MetadataIndex` 组合进 `SemanticMap` | 不继承职责过重的主类；不引入外部数据库，与“原生内存、避免跨库 I/O”的系统定位一致    |
| 调度放哪         | `ConstraintAwarePlanner`             | 职责集中、可独立单测；执行计划可解释、可审计                                          |
| 图扮演什么角色   | 约束源，而非第 4 路召回              | 图结果与语义分数的融合语义不一致，且 `smart_search` 显式剔除 `GRAPH_TRAVERSAL`        |
| 关系查询怎么实现 | 自实现 BFS，不修复全部断链 API       | 避免依赖语义未定义的旧 API；按真实需求再补                                            |
| 关系类型倒排     | 可选组件，可降级为全边扫描           | 优先保证 P0–P2 质量，同时覆盖高频类型过滤                                            |

## 4. 方案设计

### 4.1 总体执行计划

```
QueryConstraints
  → 每类叶子谓词独立 resolve → CandidateSet
  → AND 求交（CandidateSet.intersect）
  → |C| / N < 0.2 ?
      ├─ 是：pre-filter，候选集作为 candidate_uids 下推
      └─ 否：post-filter，先取 max(3k, 50)，不足时翻倍，最多 2 次
  → smart_search 多路召回 / 融合 / 重排
  → 按候选集最终校验 → 截断 top_k
```

执行计划 `ConstraintExecutionPlan` 记录 `candidate_set`、`mode`（`pre_filter` / `post_filter` /
`none`）、`retrieval_top_k`、`mode_reason` 与 `dropped_constraints`。退化候选集默认返回空；
配置 `FallbackPolicy(on_degenerate="drop_constraint")` 时逐项放宽并记录丢弃的约束来源，
保证“宁可少答，也不静默违反硬约束”。

### 4.2 属性索引与时间索引

- **按需注册**：`register_filterable_fields(...)` 为字段选择索引类型（`hash` / `sorted`），
  未注册字段仍按同样的取值顺序扫描；
- **统一取值顺序**：`getattr(unit, field)` → `unit.raw_data.get(field)` → `unit.metadata.get(field)`，
  索引查询与线性基线保持一致；
- **`HashIndex`**：`field → value → Set[uid]` 倒排；支持 `eq` / `in` / `ne`；列表、元组、集合、
  frozenset 与 dict 按键值投影，容器字段也能精确匹配；遇到不可投影值时，该字段退回扫描；
- **`SortedIndex`**：以 epoch float 排序，用 `bisect` 回答 `gt/gte/lt/lte` 区间，选择率为精确值；
- **`TimestampNormalizer`**：兼容 ISO、epoch、LoCoMo 风格字符串；不可解析值在扫描中跳过，
  非法查询边界在声明期直接报错；
- **维护方式**：写入链增量 add/remove，删点同步清理；`save_map/load_map` 持久化
  `field_kinds`，重启后自动恢复注册表；冷层 payload 通过 `_index_cold_units`
  （semantic_map.py:608）按批补建索引。

### 4.3 关系约束

- `RelationConstraintResolver` 直接遍历 `SemanticGraph.rx_graph`，按 `direction`
  （`successors` / `predecessors` / `both`）、`max_depth` 与可选 `relation_types` 做 BFS；
  访问集合去重，产出可达节点 UID 集合；
- `RelationTypeIndex`（relation_type_index.py:39）维护“关系类型 → 边”倒排，覆盖增边、删边、
  删点路径；未启用或不可用时退回全边扫描；
- 该路径不依赖 `SemanticGraph` 中调用未定义方法的三处断链 API，避免新能力依赖已知缺陷。

### 4.4 候选集代数与调度

- `CandidateSet` 提供 `intersect` / `union` / `difference` 与 `selectivity`，为后续 OR/NOT
  组合树预留代数能力；当前 `QueryConstraints` 只暴露扁平 AND；
- 选择率阈值默认 `0.2`：低于阈值走 pre-filter，把候选集透传为 `candidate_uids`；
  高于阈值走 post-filter，先把检索池放大到 `max(3k, 50)`，若结果仍填不满 `top_k` 再翻倍，
  最多 2 次；
- 最终结果必须再次按候选集校验，覆盖图扩展、后端近似过滤等可能返回候选集之外单元的环节；
- 降级与审计：`mode_reason` 解释路径选择；`dropped_constraints` 记录被放宽的谓词；
  每次放宽约束都写 warning 日志。

### 4.5 与现有 API 的衔接

- 公共门面：`SemanticGraph.search_constrained(query_text, constraints=None, top_k=10, return_score=False, ...)`（semantic_graph.py:1115），内部委托 Planner；
- 底层仍调用 `MultiRetriever.smart_search`，约束只通过 `candidate_uids` 与结果校验进入；
- BM25 / SPLADE / Cosine **零修改**；不新增召回源，不修改 `BaseRetriever` 抽象签名；
- 索引注册表随 map 快照持久化；基准脚本 `examples/bench_constrained_retrieval.py` 可离线复现。

### 4.6 方案对比


| 方案                                     | 做法                                                    | 判断                                                                                                 |
| ------------------------------------------ | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| A 仅后置线性过滤                         | 语义召回后调用 `filter_memory_units`                    | 实现最省事，但召回池可能不含满足约束的单元，无法保证填满 `top_k`；全库过滤仍需扫描                   |
| B 图作为第 4 路召回                      | 图检索结果与语义结果并集融合                            | 图结果不能表达“必须满足”的硬约束；且 `smart_search` 剔除 `GRAPH_TRAVERSAL`，接入方式与现有链路冲突 |
| C 外部数据库/搜索引擎                    | 属性/时间入 SQL 或 ES，关系入图库                       | 跨库 I/O 与同步成本高，违背内存原生、低延迟的系统定位                                                |
| D 改造每路检索器                         | 三个后端各自实现约束下推                                | 逻辑重复、破坏多态，失去“后端零修改”的复用优势                                                     |
| **E 约束下推 + 候选集代数 + 自适应调度** | **Resolver 求值 → CandidateSet 求交 → pre/post 选择** | **采用**：硬约束由最终校验保证；高选择性场景避免全库扫描；后端零修改                                 |
| F 全量扫描 + 重排                        | 扫描全库满足谓词的单元后统一排序                        | 可作为正确性基线，但复杂度 O(N)，无法满足效率目标                                                    |

§5 逐条核验方案建议所依赖的关键代码事实，并记录相应的修正与工程判断。

## 5. 对大模型生成分析结果的验证与修正

### 5.1 工作方法

课程要求结合源码、运行结果和实验验证大模型的建议，修正与实际情况的偏差。实践流程为：

**大模型建议 → 定位到具体文件与行 → 静态核验（调用链/签名/数据结构）或最小实验 → 采纳 / 修正 / 弃用，并记录理由。**

具体做法：

1. 先让模型给出“代码结构摘要 + 调用链猜测”，再用 `rg` 检索并阅读源码，逐条对照；
2. 对“方法是否存在、参数如何透传”这类判断，必须定位到定义处与调用点，不能只依据 README 或模型描述；
3. 对性能或行为上的判断，先写最小复现脚本或单测，再决定是否进入方案；
4. 把“模型说对了什么、说错了什么、为什么”整理为 §5.2 的核验表，作为后续阶段的判断依据。

### 5.3 由此形成的工程判断

1. **扩展点要落在既有签名上**：`candidate_uids` 是现成的扩展点。与新增召回源（需改枚举与加载链）相比，它的改动代价低一个数量级；先穷尽既有接口，再考虑新增入口。
2. **先正确性、后性能**：P0 用线性扫描跑通端到端并建立等价性基线，P1 再换索引、量化收益，避免“索引写对了但语义错了”的返工。
3. **不信任未核验的结论**：时间戳位置、方法存在性这类“细节假设”一旦错误，会让整个方案偏离方向；第 4 条直接推翻了“复用现成图 API”的思路。
4. **组合优于继承、门面优于扩散**：不继承职责过重的 `SemanticMap`，不向 `smart_search` 添加大量参数；新职责进入新对象，由门面统一暴露。
5. **主动裁剪范围**：关系类型倒排收益边际递减且维护语义需自行补齐，先降级为可选；主线价值在“候选集生成 + 自适应执行计划”。
6. **设计要覆盖冷数据与重启**：只在 L1 上验证等价性不够；分层存储下索引必须能回答冷数据的约束查询，重启后也要能恢复注册表与索引。

### 5.4 核验发现的既有缺陷（关系约束的前置风险）

`SemanticGraph` 有三个方法调用了 `GraphRetriever` 上并不存在的方法（全仓库仅有调用点、无定义，运行时必抛 `AttributeError`）：


| 调用点                                                                 | 被调用方法                                                                 | 现状                                                                                           |
| ------------------------------------------------------------------------ | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `search_graph_relations(seed_nodes=...)`（semantic_graph.py:1161）     | `edge_bfs_search`                                                          | 未定义                                                                                         |
| `search_graph_nodes(search_method=...)`（semantic_graph.py:1126-1132） | `hybrid_node_search` / `_node_similarity_search` / `_node_fulltext_search` | 名称不一致：实际仅有 `_hybrid_node_search` / `_semantic_node_search` / `_fulltext_node_search` |
| `get_node_neighbors`（semantic_graph.py:1204）                         | `get_relevant_nodes`                                                       | 未定义                                                                                         |

**实现期的修复状态（P3/P4）**：`search_graph_nodes` 的名称漂移与 `RetrievalMethod` 惰性导入已修复，三条派发路径可用；`get_node_neighbors` 的导入错误已消除，但 `get_relevant_nodes` 仍缺失；`search_graph_relations(seed_nodes=...)` 依赖的 `edge_bfs_search` 仍未实现。已决定不实现这两项缺失方法：没有调用方，返回形状也与约束谓词的目标不符。

**对策**：关系约束不得复用这些断链 API；`RelationConstraintResolver` 直接操作 `rx_graph` 实现 BFS。断链修复作为可选任务，也可作为分析与修复过程的记录，不阻塞主线。

| 2 | `ConstraintGroup` 可表达 AND/OR/NOT | 仅落地扁平 AND；`CandidateSet` 支持 union/difference，但查询语法未暴露                                                            | 表达力受限；OR/NOT 列为阶段 3 扩展点                          |
| 3 | 冷层/重启索引列为验收项             | `_index_cold_units` 在 `connect_to_l2` 后按 256/批补建，不回填 L1                                                                 | 消除静默漏数据；启动时间随冷层规模线性增长                    |
| 4 | 索引查询与线性基线需对齐取值顺序    | 三条路径统一为 `getattr` → `raw_data` → `metadata`；扫描路径复用时间归一化                                                      | 等价性对拍成立；混合格式时间不再漏匹配                        |
| 5 | Planner 以选择率阈值决策            | 增加 `mode_reason`、有界池扩容（最多 2 次）、`FallbackPolicy`、`dropped_constraints`                                              | 决策可解释、可审计；真实后端阈值仍待标定                      |
| 6 | 断链图 API 可修复后复用             | 仅做最小修复：`search_graph_nodes` 名称漂移与惰性导入、`get_node_neighbors` 导入；`edge_bfs_search` / `get_relevant_nodes` 不实现 | 关系约束继续走自实现 BFS；两项缺失 API 待有真实需求再定义语义 |
| 7 | 真实数据集效果对比                  | LoCoMo / LongMemEval 尚未运行；全部数字来自合成语料 + dummy encoder                                                               | 不能外推为真实语义质量；阶段 3 首先补齐                       |

### 6.5 阶段结论与后续工作

**已由实现验证的判断**：

1. “扩展点落在既有 `candidate_uids` 签名上”可行——三路检索器零修改，新增能力全部通过组合与门面接入；
2. “约束解析 + 候选集代数 + 选择率调度”的分层成立——高选择性场景下 recall / 填满率由 16.7%
   提升到 100%，宽约束场景下由 51.0% 提升到 100%；
3. 索引维护成本可控——本规模下增量 add 约 7.8 μs/单元，常驻约 248.5 B/单元；
4. 冷层与重启路径已得到覆盖——快照重启后冷 payload 可被约束索引解析，且不会被误唤回 L1。

**仍未回答的问题**：

1. **真实语义效果**：合成语料的 recall 只反映执行策略，不能替代 LoCoMo / LongMemEval 评测；
2. **后端 `candidate_uids` 语义**：仍需确认具体后端把它当前置选择器还是结果后过滤，
   这决定阈值与端到端收益的最终口径；
3. **表达力**：OR/NOT 组合树未实现，当前只支持四类叶子谓词的扁平 AND；
4. **冷层规模的持久化**：当前重启补建为 O(冷数据量) 解码；冷层远大于内存时应把倒排持久化为独立列族；
5. **两项缺失图 API**：`edge_bfs_search` / `get_relevant_nodes` 保持未实现，若未来出现真实调用需求，
   需先定义方向、深度与返回形状。

**下一步**：在 LoCoMo / LongMemEval 上构造组合查询测试集，按三种执行策略（全量/后置过滤、
固定下推、自适应）对比 recall@k / nDCG / 约束命中率 / P50 / P99，并据真实后端结果标定选择率阈值；
随后再决定 OR/NOT 与冷层索引持久化是否进入实现范围。

---

## 7. 总结

本报告围绕 Mandol 组合查询能力的缺失，依次讨论系统理解、需求分析、对象建模、方案设计、
大模型结论核验与原型实现，并在最后给出判断。

1. **问题定位**：现有检索是“多路召回 + 分数融合（并集）”，属性、时间、关系只能后置过滤或
   全库扫描；系统缺少“交集 + 谓词下推”的候选集生成层与调度层。
2. **方案设计**：以 `QueryConstraints` 声明约束，Resolver 策略族将属性、时间、关系、空间
   统一求解为 `CandidateSet`，Planner 按选择率在 pre-filter 与 post-filter 之间自适应；
   扩展点落在既有 `candidate_uids` 签名上，三路检索器零修改。
3. **核验与修正**：源码核验修正了三个关键初始判断：三路后端已支持候选集过滤，图 API 存在
   断链，时间戳不在 `metadata`。据此改为“复用既有接口、自实现关系 BFS、图仅作约束源”，
   并以 P0 线性基线保证语义等价。
4. **实现与证据**：P0–P4 已落地，103 项测试通过；合成语料上高选择性 recall@10 由 16.7%
   提升到 100%，宽约束由 51.0% 提升到 100%，约束解析层相对线性扫描加速约 40–87 倍，
   索引增量维护约 7.8 μs/单元。
5. **边界**：OR/NOT 组合树、真实数据集评测、后端 `candidate_uids` 语义确认、冷层倒排持久化
   仍未完成；现有数字只证明执行策略与索引成本，不能外推为真实语义效果。

总体判断：方案的主要贡献是把分散的属性、时间与图能力统一为可组合、可调度、可审计的约束层，
而不是再增加一个检索器。原型验证了在既有系统上以最小侵入方式获得组合查询能力的可行性。
