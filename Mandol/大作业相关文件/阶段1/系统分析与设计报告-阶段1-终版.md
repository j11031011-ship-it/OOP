# Mandol 融合索引增强：系统分析与设计报告（阶段 1）

- 课程：《大模型辅助的面向对象软件分析、设计与开发》大作业
- 方向：融合索引增强——约束下推式组合检索
- 版本：阶段 1 定稿
- 口径：全部数字来自离线合成语料（2000 units、确定性 dummy encoder、无网络、无模型下载）；
  LoCoMo / LongMemEval 真实数据实验尚未执行，相关结论不外推

---

## 0. 摘要

**问题**：现有融合检索是"三路并行召回 + 分数融合（并集）"，语义相似之外的条件只能后置过滤或
全库扫描；更关键的是三条结构性缺陷——**并集语义**无法表达"必须满足"，**裁剪不可逆**会把符合
约束但排序靠后的记忆永久截掉，**裁剪层按塔优先级仲裁**让图证据几乎无生存空间。约束信号来得太晚。

**方案**：在路由之前加"推断层 + 约束层"。查询先变成约束对象（`QueryConstraints`），由四类
Resolver 求值为统一候选集（`CandidateSet`），再在塔内把候选集下推为 `candidate_uids`，之后
S4–S9 原样执行。两道闸门兜住自动抽取的误判，五分支路由决定"空集短路 / 只传空间 / 下推"。

**新增对象**（§4.2 详列）：值对象 `QueryConstraints` / `CandidateSet`；Resolver 策略族（属性 /
时间 / 关系 / 空间）；索引族 `MetadataIndex` + `HashIndex` / `SortedIndex` +
`TimestampNormalizer` + `RelationTypeIndex`；调度与审计 `ConstraintAwarePlanner` /
`ConstraintExecutionPlan` / `FallbackPolicy`；推断 `ConstraintInferrer`。既有类只做组合式改造
（不继承、不改后端）。

**状态**：P0–P4 与统一入口 M0–M4 已落地，**144 项测试通过**。合成语料上高选择性 recall@10 由
16.7% 提升到 100%，宽约束由 51.0% 提升到 100%；约束解析层相对线性扫描加速 40–87×；索引增量
维护约 7.8 μs/单元。真实语义效果待阶段 3。

## 1. 检索方面代码分析

### 1.1 核心对象


| 对象            | 职责                                                                           | 对本工作的含义                                                                                                                                                                          |
| ----------------- | -------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `MemoryUnit`    | 记忆最小单元：`uid` + `raw_data`，并提供检索文本派生视图                       | 检索文本按 `text_content / content / description / summary / title / message` 优先级提取；`created_time` 默认 `None`、写入路径不填充（memory_unit.py:10-65、semantic_map.py:3031/3127） |
| `SemanticMap`   | 唯一真相源：集中持有记忆字典、`uid ↔ int_id`、FAISS、空间成员、稀疏检索器句柄 | 典型的"上帝类"；`filter_memory_units` 是 10 操作符的**线性后置扫描**（semantic_map.py:3245），不在多态调度内                                                                            |
| `SemanticGraph` | 用 rustworkx 有向图维护记忆间关系（时序、引用、状态更新）                      | `add_relationship` 是关系维护唯一入口（semantic_graph.py:616）；对外以门面包装 `SemanticMap`                                                                                            |
| `MemorySpace`   | 只记录成员归属（哪些 uid 属于本空间、有哪些子空间），不持有数据                | 空间谓词的天然候选集来源                                                                                                                                                                |

检索接口体系的关键衔接点：BM25 / SPLADE / Cosine 的具体实现**均已显式声明**
`search(query, top_k, candidate_uids=None, space_names=None)`，抽象基类以 `**kwargs` 透传
（bm25_retriever.py:1499-1574、splade_retriever.py:959-997、semantic_map.py:2239-2266）。
**候选集下推无需修改任何后端**，这是本方案最重要的复用缝。

### 1.2 检索链（S1–S9）


| 段          | 位置                | 做什么                                                        |
| ------------- | --------------------- | --------------------------------------------------------------- |
| S1 路由     | `_route_towers`     | 规则表 → 塔开关 + 每塔召回预算                               |
| S2 分发     | `_dispatch_towers`  | 按开关并行跑三塔                                              |
| S3 塔内召回 | 各塔检索器          | 每塔三路（BM25 / SPLADE / Cosine）并行后融合排序              |
| S4 合并     | `_build_candidates` | 各塔候选汇成全池，**全池** min-max 归一化写入 `ce_score`      |
| S5–S7 裁剪 | 级联剪枝            | 三级只做减法：MAD 截尾 → 跨塔仲裁（保留最优记忆）→ MMR 打包 |
| S8–S9 输出 | 重排 / 量化         | 统一重排 → 量化打分                                          |

两点结论直接决定方案形态：

1. **路由只控开关与预算，不参与打分；合并用全池 min-max，`ce_score` 是池相对的**——池一变窄，
   存活候选分数被重新拉伸，S5 的全局阈值会随池漂移（§4.8 据此改为分塔 MAD）。
2. **约束若加在 S4 之后必然失效**：候选已被 top_k 截断，符合约束却排序靠后的记忆永远进不来。
   这正是 §2.2 第二条缺陷的机制来源。

### 1.3 路由机制

路由层不参与打分，只决定"开哪几座塔"：

- **保守策略（默认）**：绝大多数问题（聚合、时间、简单事实等）三塔全开；仅在遇到"对抗类"问题时
  缩减为关系塔 + 情景塔。
- **激进策略（精准分发）**：聚合类 → 层级 + 情景；时间类 → 层级 + 关系；开放域 / 简单事实 → 三塔全开。

规则表由 `LocomoTowerRouter` / `LongMemEvalTowerRouter` 承载，输出塔开关与各塔 `top_k` 预算。

### 1.4 三塔各管一类记忆


| 塔         | 内容                                                                                                      | 回答的问题                                 |
| ------------ | ----------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| 分层塔     | L0 观察（一句话、一个动作）→ L1 摘要（一段事件的概括）→ L2 洞见（跨事件结论），三层各召回一次再按层融合 | 去"哪一层"记忆里找                         |
| 实体关系塔 | 实体（人、地点、物品）+ 关系（居住于、签租约、属于），在实体与关系两个空间召回                            | "谁和谁有关"                               |
| 情景塔     | 带时间戳的事件单元（一次经历、一段经过）                                                                  | "何时发生、先后顺序"，支持把时间注入上下文 |

### 1.5 现状能力与缺口


| 访问形态        | 现成能力                                                  | 缺口                                   |
| ----------------- | ----------------------------------------------------------- | ---------------------------------------- |
| 语义相似        | 三路召回 + RRF/加权/MMR 融合 + 重排                       | —                                     |
| 精确标识 / 空间 | uid 存取、空间成员过滤（`candidate_uids` 已支持空间子集） | —                                     |
| 属性            | `filter_memory_units` 10 操作符                           | 游离于多态体系外；无索引、无分页       |
| 时间            | 时间戳随 payload 存储                                     | 字符串、格式异构、无规范化、无有序索引 |
| 关系            | `GraphRetriever`、图上 BFS 能力                           | 与语义检索平行，不能作为附加约束       |
| 组合查询        | 无                                                        | 没有"交集 + 谓词下推"的表达与调度机制  |
| 统一入口        | 三塔链与 `search_constrained` 并行、互不调用              | 约束结果不进 S4–S9（§4.3）           |

属性、时间、关系三条是**能力缺口**，最后两条是**结构性缺口**——它们共同构成下一章的问题。

## 2. 问题与需求

### 2.1 组合查询难以实现

- **任务场景**：记忆访问同时要求语义相似、属性、时间与关系条件。
- **举例**：与内容 C 语义相近、发生在 T 之后、属于实体 E 的 1-hop 邻居、且属于空间 S。
- **现状**：三路在塔内并行召回并做分数融合，产出每塔一份统一排序；三塔取并集；没有"必须满足"
  的约束，属性、时间、关系只能后置过滤或全库扫描。

**核心问题**：如何让约束作为**硬条件**进入召回，而不是在结果上"尽量过滤"？
**范式转移**：并集 + 分数融合 → **硬约束筛选（交集 + 谓词下推）**。

### 2.2 三条结构性缺陷


| 缺陷                 | 后果与直接症状                                  |
| ---------------------- | ------------------------------------------------- |
| 并集语义             | 无法表达组合条件，只能靠排序"尽量"靠前          |
| 裁剪不可逆           | 符合条件但排序靠后的记忆被 top_k / 裁剪永久截掉 |
| 裁剪层按塔优先级仲裁 | 图证据在高优先级塔在场时几乎没有生存空间        |

**分析**：第一条是**表达能力**问题（没有约束语法），后两条是**时机**问题（约束信号来得太晚）。
三者共同指向同一个缺口：召回之前没有约束层。**目标：把约束条件提前到召回之前**，而不是交给
排序和裁剪去碰运气。

### 2.3 需求


| 需求          | 含义                                                              | 验证方式                                |
| --------------- | ------------------------------------------------------------------- | ----------------------------------------- |
| R1 表达能力   | 一条语句表达"语义 + 属性 + 时间 + 关系"的组合约束                 | 用例 U1–U3 各一条 `search_constrained` |
| R2 正确性     | 返回结果必须**硬满足**全部约束，而不是"尽量"                      | 结果逐条断言 + 与线性过滤基线等价       |
| R3 效率       | 高选择性约束下避免全库扫描与无效向量比对                          | 候选占比扫描曲线（P50/P99）             |
| R4 衔接与成本 | 不破坏现有检索流程与行为；维护成本可量化                          | 回归测试 + 构建/增量/内存三项指标       |
| R5 单入口     | 约束在召回前进入三塔主管线，之后完整走 S4–S9；不传约束时行为不变 | 无约束路径快照 + 塔下推参数白名单       |

收尾用例：U1 语义 + 时间；U2 语义 + 关系；U3 全组合；U4 `constraints="auto"` 由规则抽取器推断。

## 3. 优化分析

### 3.1 位置判定：选择在哪里做优化


| 候选位置            | 能力边界                              | 分析                                                                         |
| --------------------- | --------------------------------------- | ------------------------------------------------------------------------------ |
| 融合层              | 调权重 / RRF / 图扩展                 | 本质是**软排序**，输出仍是打分列表；无法表达硬约束，也无法保证结果集合       |
| 裁剪层              | MAD、跨塔仲裁、MMR                    | **时机太晚**：已在上游 top_k 之后，被截断的单元永远进不来（§2.2 缺陷 2、3） |
| 三个后端各自实现    | 在 BM25 / SPLADE / Cosine 内加谓词    | 同一套逻辑重复三份（加图与空间共五份），破坏多态，新增后端还要再写一遍       |
| **推断层 + 约束层** | 路由之前求出 UID 集合，塔内下推给后端 | **采用**：唯一能在"召回之前"表达硬约束、且不改后端的位置                     |

**落点**：在路由之前加一层推断和约束（把查询变成候选集），在三塔内部把候选集下推为
`candidate_uids`。

### 3.2 优化后的检索链

```
约束推断   根据查询生成约束条件
           规则 / 空间抽取 → 判断条件 → 两道闸门通过 → QueryConstraints
                                  ↓
路由（改） 按约束形态分五支
           none / space_only / empty / too_broad / filtered
                                  ↓
塔内（改） 候选集下推
           candidate_uids ∩ 本塔空间 → 三路只在候选子集内打分
                                  ↓
S4 合并归一（原样）  全池 min-max → ce_score
                                  ↓
S5–S7 裁剪（原样）   MAD 截尾 → 跨塔仲裁 → MMR 打包
                                  ↓
S8–S9 输出（原样）   统一重排 → 量化打分
```

### 3.3 源码核验对方案的影响

大模型的建议逐条对照源码后，有七处改变了方案形态（原 12 条对照表的收敛结论）：

1. **`candidate_uids` 三路已原生支持**——比预想更好，新增能力零修改接入；
2. **`filter_memory_units` 是线性后置扫描，且原实现不查 `metadata`**——只作正确性基线与 post-filter
   兜底，正式方案另建索引；P4 已把三条取值路径统一为 `getattr → raw_data → metadata`；
3. **时间戳在 `raw_data["timestamp"]`**，`created_time` 不被填充——字段解析 `raw_data` 优先，
   时间必须经 `TimestampNormalizer` 规范化；
4. **`search_graph_relations(seed)` / `get_node_neighbors` 断链**（依赖的 `edge_bfs_search` /
   `get_relevant_nodes` 未定义）——Resolver 直接操作 `rx_graph` 自实现 BFS，不修这两个 API；
5. **图不能作为第 4 路召回**：`smart_search` 入口显式剔除 `GRAPH_TRAVERSAL`
   （advance_retriever.py:937）——图只作为约束源；
6. **`TripleTowerRetriever` 零调用方、且不转发约束**——收益只能由新评测脚本度量，入口必须新增
   `constraints` 参数与六处 runner 透传；
7. **schema 词表不能只取注册字段**：基准数据从不注册字段——改为"已注册 ∪ 抽样 payload 键 ∪ uid"。

### 3.4 未采用思路


| 备选                              | 结论   | 原因                                                         |
| ----------------------------------- | -------- | -------------------------------------------------------------- |
| 融合层调权重 / 加过滤             | 未采用 | 软排序无法保证结果集合，硬约束无处安放                       |
| 裁剪层加过滤                      | 未采用 | 时机太晚，被截断单元无法召回                                 |
| 三路后端各自加谓词                | 未采用 | 重复实现（含图与空间共五份），破坏多态                       |
| 外部数据库（Milvus / PostgreSQL） | 未采用 | 与"原生内存、消除跨库 I/O"的系统设计冲突                     |
| 继承 `SemanticMap` 派生子类       | 未采用 | 组合优于继承：父类已职责过重，索引生命周期与存储主类不同     |
| 新增 `RetrievalMethod` 召回源     | 未采用 | 需同时改枚举与 `_ensure_retriever_loaded` 加载链，不是零改动 |

## 4. 方案设计（新增类与对象）

### 4.1 三条建模原则

1. **值对象隔离**：约束条件与候选集都是不可变/半不可变值对象，下游不区分来源，避免裸 dict 传参；
2. **策略多态**：约束与索引均为策略族，新增一种约束类型或索引结构不需要修改调度代码（OCP）；
3. **组合优于继承**：不继承职责过重的 `SemanticMap`，索引与调度以组合方式注入（SRP）。

### 4.2 新增对象总表（实现方案的核心）

**（1）值对象**


| 对象                               | 职责                                                                                                                     |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| `QueryConstraints`                 | 声明式组合约束：`metadata_filters` / `time_range` / `relation` / `space_names`；声明期校验方向、深度、seed、字段与操作符 |
| `TimeRange` / `RelationConstraint` | 叶子谓词值对象：时间区间；关系一跳（seed + 方向 + 深度 + 关系类型）                                                      |
| `CandidateSet`                     | `frozenset[uid]` + 选择性估计 + `intersect / union / difference`；**Resolver 与 Index 两轨的解耦媒介**                   |
| `ConstraintExecutionPlan`          | 执行记账：`mode` / `mode_reason` / `selectivity` / `dropped_constraints`                                                 |

**（2）约束解析策略族**


| 对象                          | 职责                                                 |
| ------------------------------- | ------------------------------------------------------ |
| `BaseConstraintResolver(ABC)` | 统一接口 `resolve(context) -> CandidateSet`          |
| `MetadataConstraintResolver`  | 属性等值/包含约束 → 查 `MetadataIndex`              |
| `TimeRangeConstraintResolver` | 时间范围 → 查 `SortedIndex` + `TimestampNormalizer` |
| `RelationConstraintResolver`  | 关系约束 → 图上限制深度 BFS（方向 / 深度 / 类型）   |
| `SpaceConstraintResolver`     | 适配器：包装现有空间成员逻辑，使其与其他谓词同构     |

**（3）索引族**


| 对象                  | 职责                                                                                                                  |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `MetadataIndex`       | 门面 + 简单工厂：`register_filterable_fields(...)` 为每个字段选择 `BaseIndex` 实现                                    |
| `BaseIndex(ABC)`      | 索引契约：`add / remove / lookup(condition) -> CandidateSet` 与 `estimate_selectivity(condition)`                     |
| `HashIndex`           | 等值类倒排 `field → value → Set[uid]`；支持 `eq/ne/in/nin`；list/tuple/set/mapping 按值投影，不可投影则回退线性扫描 |
| `SortedIndex`         | 时间/数值类 epoch float 有序数组 + bisect；支持 `gt/gte/lt/lte`；区间计数给出**精确**选择率                           |
| `TimestampNormalizer` | 多格式时间字符串 → epoch float（容错解析 + 缺省策略）                                                                |
| `RelationTypeIndex`   | 关系类型倒排 `relation_type → List[edge]`；类型过滤不再全边扫描                                                      |

**（4）调度、回退与推断**


| 对象                                      | 职责                                                                                          |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `ConstraintAwarePlanner`                  | 选择率自适应：按候选占比（选择性）决定 pre-filter / post-filter，组装执行计划                 |
| `FallbackPolicy`                          | 默认 `return_empty`；显式 `drop_constraint` 才放宽，并写入 `dropped_constraints`              |
| `ConstraintInferrer`                      | 规则引擎：query → schema 绑定 → 四类规则 → `InferredConstraints`（置信度 / 来源 / 丢弃项） |
| `InferredConstraints` / `InferenceSchema` | 推断结果值对象；schema 词表 + 字段类型 + 算子白名单                                           |

> **范围说明**：四类叶子谓词的扁平 AND 是本阶段的最小可用语义；`ConstraintGroup` 的 OR/NOT 树只
> 保留设计位置（候选集代数已支持 union/difference），不进入实现。

### 4.3 既有类的改造点（只组合、不继承、不改后端）

改造前，约束能力只挂在 `SemanticGraph.search_constrained` 上。它与三塔主线共享同一个
`MultiRetriever`，却**互不调用**：约束结果不进裁剪与量化，两条入口的行为也不可比。这属于
"入口不闭合"——约束层做得再完整，收益也进不了 S4–S9。因此下表的改造以"入口闭合"为第一目标。


| 既有类                                | 改造内容                                                                                                                                                                       | 为什么这样改                                                                         |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `SemanticMap`                         | 组合持有 `_metadata_index`；`add_unit` / `batch_add_units` / `delete_unit` 同步维护；L1 换出保留索引；`_index_cold_units` 连接冷层后补建；`save_map` / `load_map` 持久化注册表 | 不继承上帝类；增量维护挂在既有写入链尾部（与 `_incremental_aux_retriever_add` 并列） |
| `SemanticGraph`                       | 新增 `search_constrained` 门面；内部挂 `RelationTypeIndex`，随 `add_relationship` / `delete_relationship` / `delete_unit` 同步                                                 | 门面优于扩散；关系维护入口唯一                                                       |
| `MultiRetriever` / `BaseRetriever` 族 | **零修改**，只沿 `candidate_uids` 既有签名透传                                                                                                                                 | 现成的多态缝，代价最低                                                               |
| `TripleTowerRetriever`                | 入口增加 `constraints`；`_resolve_constraints` / `_apply_constraint_route`；`_tower_search_kwargs` / `_spaces_for_tower`；六处 runner 透传                                     | 约束必须在召回前进入塔链（R5）                                                       |
| `CascadeConfidencePruner`             | 增加 `use_raw_score`（默认 `False`），按塔分组 MAD                                                                                                                             | S4 的 `ce_score` 池相对，全局阈值会随池漂移                                          |

### 4.4 静态结构与协作

```
                    ┌─ ConstraintInferrer（"auto"）
query ──────────────┤                                   ─→ QueryConstraints
                    └─ 调用方显式声明
                                │ 闸门 A：confidence < 0.7 → 作废，走原路由
                                ▼
        ┌──────────────── ConstraintAwarePlanner ────────────────┐
        │ MetadataConstraintResolver → MetadataIndex → HashIndex   │
        │ TimeRangeConstraintResolver → SortedIndex + Normalizer   │
        │ RelationConstraintResolver → rx_graph BFS（RelationTypeIndex）
        │ SpaceConstraintResolver → MemorySpace 成员                │
        │            └─ 求交 → CandidateSet → 闸门 B：s > 0.8       │
        └──────────────────────────┬─────────────────────────────┘
                                   ▼ candidate_uids ∩ 本塔空间
        TripleTowerRetriever（S1 路由 → S2 分发 → S3 塔内召回）
                                   ▼
        S4 全池 min-max → S5–S7 裁剪（M4 可选分塔 MAD，默认关闭）→ S8–S9 重排 / 量化
```

**双轨多态**：约束解析多态（Resolver 族）× 索引实现多态（Index 族），两轨通过 `CandidateSet`
值对象解耦，可独立扩展；图 BFS 与倒排索引都只是"候选集生成器"角色下的可替换实现。

### 4.5 从推断到下推的一条通路

1. **推断**：`constraints="auto"` 时由 `ConstraintInferrer` 抽取；显式 `QueryConstraints` 直接用；
2. **闸门（仅自动抽取）**：置信度 < 0.7 或应用后收窄度 `s > 0.8` → 当作无约束；
3. **求值**：各 Resolver 独立产出 `CandidateSet`；
4. **求交**：AND 语义 `intersect`；仅空间条件时只传 `space_names`；
5. **路由**：定塔开关与预算；
6. **下推**：候选集 ∩ 本塔空间 → `smart_search`；
7. **后处理**：S4 归一 → S5–S7 裁剪 → S8–S9 重排 / 量化。


| 闸门     | 条件               | 作用范围   | 行为                                          |
| ---------- | -------------------- | ------------ | ----------------------------------------------- |
| A 置信度 | `confidence < 0.7` | 仅自动抽取 | 丢弃全部约束，分支记 `none`；宁可漏判，不误判 |
| B 收窄度 | 应用后 `s > 0.8`   | 仅自动抽取 | 约束几乎不筛人，丢弃并按 `none` 走            |

显式声明视为调用方已确认，不过闸门。**审计三元组**随结果返回：`source`（rule / declared /
none）、`confidence`（0–1）、`dropped`（被丢弃的谓词及原因）；量化载荷记录
mode / branch / confidence / source / dropped / selectivity / applied / skipped_towers / budget。

### 4.6 约束推断：规则 + schema 把 query 变成约束


| 类别 | 触发特征            | 产出          | 置信度    |
| ------ | --------------------- | --------------- | ----------- |
| 时间 | 相对时间 / ISO 日期 | `TimeRange`   | 0.8–0.95 |
| 标识 | UUID / `#id` / 编号 | uid 过滤      | 0.95      |
| 属性 | `<字段> 是/为/= 值` | eq 过滤       | 0.8 / 0.9 |
| 空间 | 空间名 / 图谱名     | `space_names` | 0.80      |

- **schema 绑定（防幻觉）**：词表 = 已注册字段 ∪ 抽样观察到的 payload 键（≤200 个 L1 单元，
  `unit.raw_data` 优先）∪ `{"uid"}`；已注册字段按索引类型收紧算子（hash: eq/ne/in/nin；
  sorted: gt/gte/lt/lte），未注册字段按抽样类型推断；词表外字段一律丢弃并记录原因。
- **严格匹配**：等值必须"见过"；相对时间必须有锚点（显式 `reference_time`，否则
  `query_timestamp`）。两者都缺时丢弃该谓词，**不用 `time.time()` 兜底**——否则同一查询在不同
  时刻得到不同约束，测试与评测都不可复现。
- **聚合与审计**：多项约束按 `min` 置信度聚合（木桶效应）；丢弃项记录 `field:<name>:not_in_schema`
  或 `time:no_reference_time`。

### 4.7 候选集生成


| 谓词 | 实现          | 要点                                                                                                   |
| ------ | --------------- | -------------------------------------------------------------------------------------------------------- |
| 属性 | `HashIndex`   | 倒排 `field → value → Set[uid]`；支持等于、不等、包含、不包含；列表/字典按键值投影，不可投影回退扫描 |
| 时间 | `SortedIndex` | 排序 + bisect 定位区间；支持大于/大于等于/小于/小于等于；入口先经 `TimestampNormalizer` 统一格式       |
| 关系 | 图上 BFS      | 遍历图数据库、访问集合去重；支持后继/前驱/双向，限制 `max_depth` 与关系类型                            |

### 4.8 执行计划：选择率自适应

- **阈值**：`候选数 / 总量` 小于阈值（默认 20%，随库规模与后端代价标定，不写死）→ 把候选集作为
  `candidate_uids` 透传，走 pre-filter；否则不做下推，检索后过滤。判据写入
  `ConstraintExecutionPlan.mode_reason`。
- **post-filter 必须填满 top_k**：先沿用既有 `max(top_k*3, 50)` 扩容取法；仍不足时按
  `ceil(top_k / 选择率)` 有界扩容，最多 2 次，避免无界重试。
- **回退不能静默**：默认返回空（`return_empty`）；放宽某条约束必须显式配置（`drop_constraint`），
  并把丢弃项写入 `dropped_constraints`，否则"无解"会悄悄变成"另一个查询"。
- **语义相似度只作排序信号最后介入**，保证重排不浪费在被过滤掉的候选上。

**入口与塔内下推（统一入口 M0–M4）**：


| 分支         | 条件                                               | 行为                                                                 |
| -------------- | ---------------------------------------------------- | ---------------------------------------------------------------------- |
| `none`       | `constraints is None`、`is_empty()`、或闸门 A 不过 | 原路由原样，与改造前逐字节等价                                       |
| `space_only` | 只有 `space_names` 且空间可寻址（三个塔根空间）    | 由空间反推塔并覆盖路由；**不物化 UID**                               |
| `filtered`   | 其余                                               | `ConstraintAwarePlanner` 求交，按 `s` 判闸门 B                       |
| `empty`      | 解析为空，或空间未挂载                             | 派发前短路，返回完整载荷（`results=[]`、`context=""`、routing 骨架） |
| `too_broad`  | `s > 0.8`                                          | 丢弃约束，按 `none` 走                                               |

- **预算**逐塔放大：`max(1, min(ceil(topk_i / s), 4 × topk_i))`；`final_top_k` 不放大，避免
  "约束越紧、输出越多"的越权。
- **塔内白名单**：三个塔共六处 runner 只透传 `methods`（分层塔除外）、`candidate_uids`、
  `space_names`；`constraints` 在管线开头被 `pop`，不会漏进 `smart_search`。嵌套空间
  （如 `hierarchical_memory:L2_Insight:Timeline`）不可寻址，走 `filtered` 分支物化 UID；
  未挂载空间只记 `dropped`，**绝不用于关塔**（否则会误关全部三塔）。
- **S5 改分塔原始分 MAD**：`use_raw_score` 开启后按 `tower_source` 分组，取
  `raw_metadata["original_score"]`（缺失回退 `ce_score`），每组各算 `median − 2.5·MAD`；
  组内 `n < 2` 或 `MAD < 1e-6` 时整组保留。S6 跨塔仲裁与 S7 MMR 仍用统一量纲的 `ce_score`。

### 4.9 设计取舍


| 取舍点       | 选择                                 | 理由                                                                    |
| -------------- | -------------------------------------- | ------------------------------------------------------------------------- |
| 约束逻辑放哪 | 独立 Resolver 族 + Planner           | 不放 `BaseRetriever` 子类：约束求值与评分召回是两类职责，后者会违反 DRY |
| 索引挂哪     | `MetadataIndex` 组合进 `SemanticMap` | 不继承上帝类，不引入外部数据库                                          |
| 怎么衔接检索 | 复用 `candidate_uids` kwargs 链路    | 零修改三路后端，并直接受益于既有空间过滤缓存                            |
| 约束从哪来   | 显式声明优先，`"auto"` 走规则抽取    | 显式约束可复现；自动抽取必须带置信度与丢弃审计                          |

## 5. 总结与遗留

1. **检索流程**：九段串联；路由只控开关与预算；合并用全池 min-max；三级裁剪只做减法。
2. **问题**：并集语义、裁剪不可逆、塔优先级硬碾压——约束信号来得太晚。
3. **定位**：融合层无法硬约束、裁剪层太晚、后端重复实现；约束层落地后又暴露"入口不闭合"，
   合适处是**推断层 + 候选集层**。
4. **方案**：系统从查询推断约束 → 两道闸门 → Resolver 求值 → 路由与塔内下推 → S4–S9；
   新增对象以"值对象 / Resolver 策略族 / 索引族 / 调度与审计 / 推断"五组组织（§4.2）。

一句话概括：把分散的属性、时间与图能力统一为**可组合、可调度、可审计**的约束层，并让约束有了
自动来源；约束是塔链的**召回前置条件**。

**遗留问题**：

1. **真实语义效果**：合成语料的 recall 只反映执行策略，须在 LoCoMo / LongMemEval 上补齐；
2. **后端 `candidate_uids` 语义**：仍需确认是前置选择器还是结果后过滤，这决定阈值口径；
3. **表达力**：OR/NOT 组合树未实现，当前为四类叶子谓词的扁平 AND；
4. **冷层持久化**：重启补建为 O(冷数据量) 解码，冷层远大于内存时应把倒排持久化为独立列族；
5. **两项缺失图 API**：`edge_bfs_search` / `get_relevant_nodes` 保持未实现，若出现真实调用需先
   定义方向、深度与返回形状；

**阶段 2 首项工作**：在 LoCoMo / LongMemEval 上构造组合查询测试集，对比纯语义 / 语义 + 线性
后置过滤 / 本方案三者的 recall@k、nDCG、约束命中率、空结果率与 P50/P99，并据真实后端标定
选择率阈值；随后再决定 OR/NOT、冷层索引持久化与默认翻转是否进入实现范围。
